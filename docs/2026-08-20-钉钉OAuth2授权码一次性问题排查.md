# 钉钉 OAuth2 扫码登录"不合法的临时授权码"排查记录

> 日期：2026-08-19 ~ 2026-08-20
> 现象：浏览器打开 `https://test.nekomiao.com/#/login` → 钉钉扫码授权 → 回调后报错"钉钉授权未完成，请重试"，后端日志 `invalidParameter.authCode.notFound`（不合法的临时授权码）。
> 耗时：跨越多轮排查（约 2 小时），最终根因是一个**看似无害的"优化"引入的一次性授权码消费问题**。

---

## 一、现象与影响

- 用户在**普通浏览器**（非钉钉容器）打开登录页，走 **OAuth2 网页扫码登录**（`login.dingtalk.com/oauth2/auth`）
- 钉钉授权页**正常弹出**（显示"校友安居 - 钉钉统一身份认证"），扫码/确认后正常回跳
- 回跳到 `/api/auth/dingtalk/callback` 后，后端兑换 authCode 失败：
  ```
  dingtalk oauth2 token failed: status=400 body={
    "code":"invalidParameter.authCode.notFound",
    "message":"不合法的临时授权码"
  }
  ```
- 前端被重定向到 `/login?error=auth_failed`，弹窗"钉钉授权未完成，请重试"
- **下午本地测试是成功的，同一套代码/凭证晚上部署到线上后失败** —— 这是最迷惑的点

---

## 二、排查过程（按时间线）

### 阶段 1：怀疑兑换接口不对

先入为主的判断：企业内部应用的 authCode 应该走**旧版免登接口**（`topapi/v2/user/getuserinfo`）或 **sns 扫码接口**（`sns/getuserinfo_bycode`）。

- 尝试 1：改走 `sns/getuserinfo_bycode`（HMAC-SHA256 签名）→ 报 `40014 不合法的access_token`（签名参数放错位置）
- 尝试 2：签名参数改放 URL query → 报 `40078 不存在的临时授权码`
- 结论：**sns 体系与 login.dingtalk.com 的 OAuth2 授权码不通用**，方向错误

### 阶段 2：回滚到"下午版本"仍然失败

通过 git reflog 确认下午 17:21 部署的是 commit `438e081`，回滚后**仍失败** → 排除代码差异？(其实没排干净，见阶段 4)

### 阶段 3：怀疑凭证/配置/环境

- 验证 `gettoken`（appKey/appSecret）正常 ✅
- 对比本地/线上 `.env` 凭证一致 ✅
- 对比前端 dist 的 client_id / 回调地址一致 ✅
- 授权 URL 用 curl 实测：302 → challenge.htm，标题"校友安居 - 钉钉统一身份认证" ✅ 应用识别正常
- 结论：凭证、URL、scope、应用识别全部正常，**问题不在这些**

### 阶段 4：关键突破 —— 对比"下午成功版本"与"当前版本"的完整 diff

`git diff 438e081 HEAD -- DingTalkClientImpl.java` 暴露了差异：

**下午成功版本（438e081）**：
```java
String userAccessToken = exchangeOAuthCode(authCode);  // 直接用 OAuth2 兑换
```

**当前失败版本（2a6d543 引入的"优化"）**：
```java
// 优先尝试：OAuth code 直接调 getuserinfo（企业内部免登接口）
try {
    String userId = fetchUserIdByCode(authCode, appToken);  // ← 先消耗了一次 authCode
    ...
} catch ...
// 降级：再用同一个 authCode 兑换
String userAccessToken = exchangeOAuthCode(authCode);      // ← 已被消费，失败
```

### 阶段 5：根因确认

**钉钉 OAuth2 授权码是一次性的（5 分钟内有效、只能使用一次）**。
commit `2a6d543`（"优化OAuth登录流程，增加直接获取用户信息的尝试"）在真正的 OAuth2 兑换**之前**先调用了 `getuserinfo` 接口试探 —— 即使该接口返回错误（40078），**钉钉也已把授权码标记为已使用**，导致随后 `userAccessToken` 兑换拿到的是**已消费的授权码** → `invalidParameter.authCode.notFound`。

下午测试成功的版本没有这个抢先尝试，**直接兑换**，所以正常。

### 修复

```java
// getUserIdByOAuthCode：直接兑换，不做任何前置试探
String userAccessToken = exchangeOAuthCode(authCode);  // 一次性授权码，必须第一个用
String unionId = getUnionIdByUserToken(userAccessToken);
return getUserIdByUnionId(unionId);
```

---

## 三、根因总结

| 项 | 说明 |
|---|---|
| **直接原因** | OAuth2 授权码被 `getuserinfo` 抢先消耗，后续兑换拿到已消费的 code |
| **间接原因** | 一次"优化"在兑换前加了无谓的接口试探，未意识到授权码的一次性语义 |
| **放大的迷惑** | ① 多个可能的兑换接口（getuserinfo / sns / userAccessToken）让人误判方向；② 下午本地成功、晚上线上失败，让人误以为是环境差异 |

---

## 四、经验教训（重要）

1. **钉钉 OAuth2 授权码（authCode）是一次性的**：5 分钟有效、只能使用一次。任何先用它调接口的行为（哪怕返回错误）都会消耗它。拿到授权码后**必须直接用于 `userAccessToken` 兑换**，不要做任何前置试探/降级重试。
2. **"优化"要警惕副作用**：在关键链路上加"先尝试 A 再回退 B"的逻辑，要确认 A 不会消耗共享的稀缺资源（一次性 token/code）。
3. **对比要找对基线**：不要凭记忆判断"代码没变"，用 `git diff <下午版本> HEAD` 精确对比。本次正是因为先对比了错误的基线（2a6d543 而非 438e081）多绕了一圈。
4. **接口选型要分清体系**：
   - 企业内部应用 JSAPI 免登 → `topapi/v2/user/getuserinfo`
   - 浏览器 OAuth2 网页扫码（login.dingtalk.com）→ `v1.0/oauth2/userAccessToken` + `v1.0/contact/users/me`
   - 旧版扫码登录（qrconnect）→ `sns/getuserinfo_bycode`（HMAC-SHA256）
   - **三者授权码不通用**，混用必然报"授权码不存在"
5. **诊断要记录关键指纹**：authCode 长度/头、clientId、完整钉钉响应、回调完整参数（code/authCode 双参数名），这些日志让根因对比成为可能。
