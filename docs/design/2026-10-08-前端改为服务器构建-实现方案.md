# 前端改为服务器构建（对齐后端部署）

> 状态：已确认方案 A，待实施
> 一句话：把前端「本地构建 + 上传产物」改成「本地一条命令 → 服务器拉代码 → 装依赖 → 构建 → 落版本目录 → 切软链」，与后端部署同构，使前端产物只有一个来源。

---

## 1. 为什么改

### 1.1 触发事实（2026-10-08 线上登录页故障）

| 事实 | 证据 |
| --- | --- |
| 登录页点不动 | 报错 `[dd] VITE_DING_APP_KEY 未配置`；线上 chunk `dd-B6_PEBnP.js` 里整个 OAuth 函数被 terser 消除成只剩一行 `console.error` |
| 出事的那份产物是**本机构建**的 | `web/current` → release `20261003_230619`，由本地 `deploy-web-remote.sh` 构建后上传 |
| 本机 `frontend/.env` 缺 `VITE_DING_APP_KEY` | 当时只有 `VITE_DING_CORP_ID` |
| **服务器的 `frontend/.env` 一直是对的** | `/root/goretire/frontend/.env` 自 2026-08-23 起就有非空的 `VITE_DING_APP_KEY` |

结论：这次故障是「本地构建」这条路径自己产生的——同一份源码，因为构建机器上 gitignored 的 `.env` 不同，产出了会挂的产物。

### 1.2 目标

1. 前端产物只有一个来源：服务器。
2. 本地不再需要 node 工具链，也不再传输产物。
3. 构建期配置缺失时**构建失败**，而不是静默产出一份坏产物。

### 1.3 非目标（明确不做）

- **不把构建期配置入库**（已确认：继续只在服务器维护 `frontend/.env`）。因此本方案达成的是「单一构建环境」，**不追求「可从仓库复现」**——服务器的 `.env` 仍是仓库外、无文档、不可 review 的状态。
- 不引入 CI（GitHub Actions / 云效）。
- 不改 nginx 配置、不改产物目录结构与软链语义、不改门户与租房 H5 的业务代码。
- 不移除本地 `npm run build`：它降级为「自己看产物」，不再用于发布。

## 4. 详细设计

### 4.1 远程 `deploy-web-ecs.sh`（承担全部工作）

沿用后端 `deploy-ecs.sh` 的结构：`pre_check` + `build` + `activate`。

| 调用 | 行为 |
| --- | --- |
| `deploy-web-ecs.sh`（无参） | pre_check → build → activate 新版本 |
| `deploy-web-ecs.sh --activate <版本名>` | 只切软链（校验两个入口齐备），不构建 |
| `deploy-web-ecs.sh --rollback` | 切到上一个版本（沿用现有实现） |
| `deploy-web-ecs.sh --current` | 打印当前版本 |

### 4.2 pre_check（任一不满足即 `exit 1`，且不做任何变更）

1. `$REPO_DIR/.git` 存在。
2. 工作区没有未提交的 **tracked** 改动（`git status --porcelain -uno` 为空）——否则 `git pull --ff-only` 会失败或产生意外结果。
3. `$REPO_DIR/frontend/.env` 存在，且 `VITE_DING_APP_KEY` 非空。这是本次事故的直接原因，必须在构建前拦住；`build-web.mjs` 里已有的门禁是同一条件的第二道。
4. `node` 与 `npm` 可用，node 版本满足 Vite 8 的要求（≥ 20.19 或 ≥ 22.12；当前 v20.20.2 落在允许区间内，首次构建实测确认），并打印实际版本便于排查。
5. `releases` 目录可创建、可写。

### 4.3 build

```
cd $REPO_DIR && git pull --ff-only
cd $REPO_DIR/root-site && npm ci        # 按 lockfile
cd $REPO_DIR/frontend  && npm ci
cd $REPO_DIR && node scripts/build-web.mjs    # 产出 $REPO_DIR/dist
mv $REPO_DIR/dist $RELEASES_DIR/<时间戳>
```

- `npm ci` 每次全量重装：与后端「每次 `mvn package`」同构，换来产物可复现。两个应用合计约 713 个包（root-site 483 + frontend 230），2 核机器上预计 1–3 分钟（估算值，首次构建计时确认）。
- 用 `mv` 而非 `cp`：产物直接成为版本目录，避免重复占用与半成品残留；下一次 `build-web.mjs` 会自己重建 `dist`。
- 时间戳格式沿用现有的 `date +%Y%m%d_%H%M%S`。

### 4.4 失败语义

构建阶段任何一步失败（pull / npm ci / 构建 / 门禁 / mv）都**不触碰 `web/current`**，线上继续服务上一版；失败时若已创建空的版本目录则清理掉。

### 4.5 本地 `deploy-web-remote.sh`（变薄）

- 默认：`ssh ecs-alr 'bash /root/goretire/scripts/deploy-web-ecs.sh'`。
- 透传 `--rollback` / `--current` / `--activate <版本名>`。
- **移除 `--skip-build`**：它原本表示「用现有本地 dist 发布」，服务器构建下没有对应语义；「不构建、只切到某个已有版本」由 `--activate` 承担。
- 不再构建、不再读本地 `dist`、不再打包上传。

### 4.6 服务器环境变更（一次性，仓库外，实施时执行）

1. `/root/.npmrc` 的 `registry` 改为 `https://registry.npmmirror.com`（当前值 404，不修则服务器装不上任何包）。
2. 首次构建会自动补装 `root-site/node_modules`。

## 5. 风险与验证

| 风险 | 影响 | 缓解 | 何时验证 |
| --- | --- | --- | --- |
| 内存不足（2 核 / 可用约 741M + 1G swap，门户 webpack 构建偏紧） | 构建 OOM 失败 | 先不加限制实测；若 OOM 则给构建加 `NODE_OPTIONS=--max-old-space-size=1024`，必要时扩 swap | 首次服务器构建（本方案唯一必须实测项） |
| 服务器 `frontend/.env` 丢失或被改错 | 构建直接失败，不会静默发坏产物 | 4.2 的 pre_check + `build-web.mjs` 门禁双保险；建议备份为同目录 `.env.bak-<日期>`（被 gitignore，且被 nginx 的 `.env.*` 拒绝规则挡在站外） | 实施时用「临时改名」手法做负向验证 |
| 与后端共用 `/root/goretire`，两边都会 `git pull` | 并发发布互相干扰 | 文档写明不要同时发布 | 文档评审 |
| 每次 `npm ci` 拉长发布时间 | 发布从秒级变分钟级 | 接受（与后端编译同构）；日后若嫌慢，可按 lockfile 哈希跳过重装 | 首次构建计时 |

## 6. 回滚

- **站点回滚**：`--rollback` 切到上一个版本目录；跨「本地构建时代」的旧版本依然可用。
- **方案回滚**：把两个脚本恢复到本次改动之前的版本即可。服务器上不引入新状态（registry 修正除外）。

## 8. 验收标准

1. 本地一条命令即完成构建并上线，本地不产生也不上传任何产物。
2. 人为清空或改名 `frontend/.env` 后执行发布：**构建失败，且线上不受影响**（`web/current` 指向与站点 HTTP 状态均不变）。
3. 发布后线上 `ali/house/assets/dd-*.js` 含 `client_id=`，且不含「VITE_DING_APP_KEY 未配置」。
4. `--rollback` 能切回上一个版本，`--current` 输出正确。
5. 发布后 `git -C /root/goretire status` 无新增 tracked 改动（产物与 `node_modules` 均被 gitignore）。
